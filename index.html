Terminal Commands

How to navigate and do things in the Terminal
Type these commands and hit "Enter"

pwd             # Print Working Directory: "Where am I right now?"
ls              # List: "What files and folders are in here?"
cd foldername   # Go down into a specific folder (child folder). Often follows 'ls'
cd ..           # Change Directory: Go up one level (parent folder)
open .          # Mac ONLY: Open your current Working Directory in Finder
start .         # Windows ONLY: Open your current Working Directory in Explorer
ctrl + c        # Cancel/Quit: Stop a running process (Same on Mac/Windows/Linux)
clear           # Clean: Clear the terminal screen so you have a blank slate

Basic Git Commands (That you will use again and again!)

Git is your Version Control system. It tracks the history of your creativity & allows you to update your webpages online.
Type these commands and hit "Enter"

Note: The # indicates a comment (an explanation). Do NOT type the # or any text after it into the terminal! 

git clone             # Download a project from GitHub
git log               # View history (Enter = scroll through more items, 'q' = exit)
git status            # See what has changed since the last save
git add .             # Stage all changes to be saved
git commit -m 'msg'   # Save the changes with a label
git push              # Upload your saves to GitHub
q                     # Quit: Use this to get out of 'git log' or stuck screens

The Development Loop (Save/Commit/Push)

This is the cycle you will repeat every time you work. Think of it as: Create/Modify → Save → Record (commit) → Upload (push).

  1. Modify: Make changes to your index.html (add text, new elements, images, etc.).
  2. Save: Press Cmd + S (Mac) or Ctrl + S (Windows) in your code editor.
  3. Record & Upload: Run these commands in your terminal:
git add .                  # Tell git to pay attention to your new changes
git commit -m 'message'    # Store your changes locally with a descriptive label (replace 'message' with your own)
git push                   # Upload your changes to GitHub
  1. Verify: Go to your browser and refresh your .github.io page.

Pro-Tip: It can take 30–60 seconds for GitHub to process your "push." If you don't see your changes immediately, wait a minute and refresh again!

You don't have to git push just to see if your code is working. We use a local server to preview changes after you save your files.

The "Live Server" Extension (Recommended)

Installing

  1. In VS Code, click the Extensions icon (the 4 squares on the left sidebar).
  2. Search for "Live Server" (the one by Ritwick Dey) and click Install.

Use:

  1. Open your index.html file so you can see your code.
  2. Look at the very bottom-right of your VS Code window and click the "Go Live" button.

Branches & Merges

Working on "branches" lets you experiment without breaking the main site.

Important Note on your Webpage: GitHub Pages is set to show your main branch (some older repos might call this master). Think of this as your Live Stage. Other branches are your Behind-the-Scenes or Rehearsal Spaces and their code will never be displayed on the actual website! 

    git checkout -b name      # Create a new branch & jump into it
git push -u origin name   # Tell GitHub this new branch exists
git branch                # List all branches (* = where you are)
git checkout main         # Switch back to the LIVE webpage version
git merge source          # Bring changes from a branch into your current branch (blends them)
git log --all --decorate --oneline --graph –pretty    # Visualize your branches

Time Travel (Viewing AND Playing with Earlier Versions)

Did you break something and want to go back? Or do you just miss an old design? Here is how you travel back in time and start over from there.

  2. Peeking vs. Staying:

    To just peek at the past: git checkout <hash>

    To stay and start a new experiment from that spot: git checkout -b <new-branch-name> <hash>

  3. Share your experiment:

    git push -u origin <new-branch-name>
  4. Build the Future:

    In this new branch, you can experiment with new ideas BUILDING on top of your earlier idea. Go ahead and get creative! Just remember to:
    git add .
    git commit -m '...'
    git push
    ...frequently to save your progress!

  5. Switching back to your latest work:

    If you want to leave the past and go back to your most recent work on a specific branch:

    git branch            # List all your available "timelines" (branches)
git checkout main     # Go back to your primary live site
git checkout name     # Jump to any other specific experiment branch

Publishing Your #1 Favourite Version

GitHub Pages always shows whatever is at the latest tip of your main branch. So if your favourite version is an older commit, your live website won't be showing it (it's showing the newest commit on main instead.)

To make your favourite version the one that appears live on the web, you need to make it the latest point on main and push it. Here's how:

  1. Find the commit hash of your favourite version: 
    git log --oneline
  2. Create a new branch from that commit: 
    git checkout -b my-favourite-version abc1234

    Replace abc1234 with the actual hash from your log.

  3. Merge that branch into main: 
              git checkout main
          git merge my-favourite-version
  4. Push main to GitHub: 
    git push

⚠️ Watch out for merge conflicts

If main has newer commits after your favourite, git may flag a conflict. When that happens, accept the incoming changes (your favourite version) — you're telling git "I want this older version to be the one people see."

Remember: your live website at username.github.io/a1-git-labyrinth only ever reflects the latest commit on main. Nothing on any other branch will ever show up there.

Clean Indentation & Hierarchy

Think of HTML like a set of nesting dolls. If a tag is inside another tag, it should be indented to the right using the Tab key. This doesn't change how the website looks to others, but it makes the code much easier for you to read!

❌ Messy (Hard to read)

Everything is flush to the left. It's hard to tell where the "body" ends and the "main" begins.

<body>
<main>
<h1>Where does this end?</h1>
</main>
</body>

✅ Clean (Professional)

Each "child" is tucked inside its "parent." Now we can see the structure clearly.

<body>
    <main>
        <h1>This is easy to read!</h1>
    </main>
</body>

Michael's Trick: If your code gets messy, you can usually fix the indentation automatically! In VS Code, right-click anywhere in your code and select "Format Document."

Resolving Common Git Errors (Don't Panic!)

If the terminal gives you a scary error message, look here first.

1. "Everything is gone!" (Detached Head)

If you checked out a commit hash and your new work isn't showing up, you are likely in "Detached HEAD" state. It just means you aren't standing on a branch.

git checkout main    # Jump back to safety

2. "Everything is red!" (Merge Conflicts)

Git found two different versions of the same line and needs you to pick a winner. In VS Code, look for these buttons above the red text:

  • Accept Current Change: Keeps the work on your computer (the version you were just typing).
  • Accept Incoming Change: Keeps the work coming from elsewhere (GitHub or the other branch).
  • Accept Both Changes: Keeps both so you can combine them manually.

Which one? If you want your new work to stay, pick Current. If you like the other version better, pick Incoming. If you pick the wrong one, press Cmd/Ctrl + Z immediately!

3. "Rejected / Non-fast-forward"

This usually happens when GitHub has work that your computer doesn't have yet (like if you edited a file directly on Github.com/your-repo).

git pull origin main   # Pull the cloud changes down to your computer

Michael's Rule: If you're stuck for more than 15 minutes, stop and ask a classmate or post a screenshot to Brightspace. Don't delete your folder and start over!

Build Your Page (the content)

Your page displays one image, five times. Each of the five sections uses CSS to transform that same image into something completely different. Think of it as a glitchy gallery — the same source, five encounters.

  1. Read the Glitch Studies Manifesto (assigned reading this week). Each of your 5 transformations must be influenced by a different idea from the manifesto. You'll label this directly on your page (see step 4).
  2. Create the five transformation sections. These can be five <div> containers, but they don't have to look like five separate panels. They may overlap, float, repeat, interrupt the page, or behave differently as the user scrolls.

    Each transformation must use at least 3 CSS properties. Choose from this list (or find more online):

    • Scale: display at a small, intentional size with deliberate placement
    • Flex/responsive: use Flexbox so resizing the browser causes dramatic change. Include a note on the page telling the user to resize their browser.
    • Tiled: use background-image and background-repeat to tile across a div
    • Filtered: use the CSS filter property pushed to an expressive extreme: blur, contrast, hue-rotation, invert
    • Fragmented: use CSS Grid to slice the image into cells with gaps, rotations, or offsets
    • Cropped/panned: use object-fit, object-position, or overflow: hidden to reveal only a fragment
    • Blended: layer multiple instances using mix-blend-mode or opacity
    • Transformed: use transform (skew, rotate, scale, perspective) taken to an expressive extreme
    • Typographic: use the image as a background behind large CSS-styled text
  3. CSS Requirements — do these as you build:
    • Create 5 custom classes defined in style.css. Each class selector must have a comment in the CSS file describing what it does: 
      /* transformation-1: filters the image to extreme high contrast */
.transformation-1 {
  filter: contrast(300%) saturate(0%);
}
    • Create 3 element IDs and define them in style.css: 
      /* #hero-section: the opening full-bleed image section */
#hero-section {
  width: 100%;
  height: 100vh;
  overflow: hidden;
}
  4. Label each transformation on the page. Each section should include a short label, caption, or note identifying:
    1. The idea/concept taken from the Glitch Studies Manifesto
    2. The CSS idea being explored
    3. How the two relate to each other

    This can be a simple <p> or <caption> — it doesn't need to be elaborate.

  5. Add comments to every block of code explaining what it does (<!-- like this --> in HTML; /* like this */ in CSS).
  6. Optionally leave commented-out sections of code that you're no longer using. These traces of your process are part of the work. Use the Better Comments extension for headings inside commented sections.
Bonus (+5%): Add a media query to your CSS file for responsive design, so your page scales gracefully to a smartphone or tablet screen size. Search google or W3Schools for how to accomplish this.

VS Code Tips

Technique How to do it Why use this?
Split Editor Right-click a file's tab > Split Right To edit/view 2 or more files side-by-side.
Move Terminal Right-click terminal header > Panel Position Moving it to the Right is great for wide monitors or if you expect a long response from a terminal command.
Split Terminal Click the Split Pane icon (looks like two boxes) For example: try running git log --oneline in one terminal, and then using the other one to checkout different commits!
Kill Terminal Click the Trash Can icon To close a terminal session, especially if a command gets stuck or buggy.
Find Text Ctrl/Cmd + F A search box appears at the top right. Use the Up/Down arrows in the bar to jump through every time that word appears in your code.
Find & Replace Ctrl/Cmd + F + Arrow Click the small arrow > to the left of the search box to open Replace mode. • Type your new text in the second box. • Click the c icon to replace just one instance. • Click the ac icon (overlapping boxes) to replace ALL instances at once.

The Power of Word Wrap

By default, long lines of code go off the screen. Word Wrap keeps everything visible without horizontal scrolling.

Fix: Gear Icon > Settings > Search "wrap" > Turn "Editor: Word Wrap" to on.

Without Word Wrap (Annoying):
<p>This is a very long line of HTML that requires you to scroll forever to the right to see the end of the sentence...
With Word Wrap (Better):
<p>This is a very long line of HTML that wraps around so you can see everything at once.
