About the Course

This course is structured around studio-based projects that approach the browser as an artistic medium. Students develop HTML, CSS, JavaScript, and p5.js skills within a professional development environment: writing code in VS Code, managing projects with git, and publishing through GitHub Pages.

Version control is treated as both a practical workflow and a conceptual framework for iterative, non-linear creative practice. Weekly studio work, lectures, and seminar discussion draw on the history of net.art and software art to situate student work within broader traditions of browser-based artistic practice. No prior coding experience is required.

Detailed walkthrough — Tuesday May 5
Step 1
Install git and configure it

Download and install git from git-scm.com/install. Once installed, open the terminal in VS Code (View → Terminal or Ctrl+`) and configure your identity:

terminal
git config --global user.name "Your Name"
git config --global user.email "you@email.com"

Use the same email address as your GitHub account.

Step 2
Set up an SSH key for GitHub

An SSH key lets you push to GitHub without entering your password every time. Follow the instructions here: docs.github.com → Connecting to GitHub with SSH

Step 3
Create your repo and enable GitHub Pages
  • Go to github.com and create a new public repo named exactly username.github.io (use your actual GitHub username)
  • Check "Add a README file"
  • Go to Settings → Pages → under Branch, select main → Save
  • Your page is now live at username.github.io — takes 1–2 minutes to appear
Step 4
Clone the repo in VS Code

In the VS Code terminal, navigate to where you want your work, then clone:

terminal
cd Documents
git clone git@github.com:username/username.github.io.git
cd username.github.io

Then: File → Open Folder to open it in VS Code.

Step 5
Install Better Comments extension
  • Extensions panel (Ctrl+Shift+X) → search "Better Comments" → Install
  • This extension colour-codes comments. Use <!-- * for section headings in commented-out code
Step 6
Create index.html and start with comments

Create a new file: index.html. Start with just a comment:

index.html
<!-- * this is my first webpage -->

Open in your browser: in the terminal type open . to open the folder, then drag index.html into the browser. The comment is invisible — comments are for you, not the visitor.

Make your first commit:

terminal
git add .
git commit -m "first file, comment only"
Step 7
Add plain text, then HTML structure

Below your comment, type your name as plain text. Save and reload — it shows up without any tags. Commit this.

Now add proper HTML structure:

index.html — boilerplate
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Your Title Here</title>
  </head>
  <body>

    <!-- your content goes here -->

  </body>
</html>

Add a heading, a paragraph, an image. Save, reload, and commit after each meaningful change.

Step 8
Push to GitHub — local vs. cloud

Your changes only exist on your machine so far. Two contexts exist:

  • Local: files on your computer, openable as a file in your browser — only you can see them
  • Cloud: your repo on GitHub, published via GitHub Pages — anyone can visit username.github.io

Push your commits:

terminal
git push origin main

Visit username.github.io — GitHub Pages takes 1–2 minutes to update after a push.

— Break —
Step 9
Branching

First, create a develop branch — your primary working branch from here on. Never commit directly to main.

terminal
git checkout -b develop

Now create a feature branch off develop:

terminal
git checkout -b your-branch-name

Make changes and commits, then push the branch to GitHub:

terminal
git push -u origin your-branch-name

To navigate your history: git log shows commit hashes. To branch from an earlier state:

terminal
git checkout -b new-branch-name abc1234

In-class exercise: create at least 2 feature branches, make meaningful changes on each, use git log and git checkout to navigate between them. Push all branches to GitHub.

— Break —
Step 10
Reading assignments

Each week a reading is posted here and on Brightspace. Before Thursday class, write a response and push it to your username.github.io index page.

Accepted formats: paragraph (~200 words), point form, sketches or photos, annotated screenshots, a short piece of code, or a hyperlinked response. Anything that shows genuine engagement with the text.

Thursday seminars begin with these responses — your notes are the conversation.

Detailed walkthrough — Thursday May 7
Step 1
Install Live Server extension
  • Extensions panel → search "Live Server" → Install
  • Right-click index.html → Open with Live Server
  • Your page now auto-reloads every time you save — no more manual refreshing
Step 2
Merging branches

Switch to develop and merge a feature branch into it:

terminal
git checkout develop
git merge your-branch-name
Step 3
Conflict resolution

A merge conflict happens when two branches change the same line. VS Code shows conflicts inline — you choose which version to keep, or combine them. Once resolved:

terminal
git add .
git commit -m "resolved merge conflict"

Assignment 01
Git Labyrinth
Due Saturday May 10, 11:59pm  ·  Weight 15%

Overview

Build a single HTML page through a process of branching, merging, and versioning using git. The page exists as five distinct versions — five parallel or sequential states that together constitute the work. The git history of your repository is part of the assignment.

Branching Strategy

Never commit directly to main. Work on a develop branch and create feature branches for each version. Merge feature branches into develop when ready. Merge develop into main only when you have a stable, presentable state.

Code Comments

Include commented-out code in each version. These are the ideas you tried, the things that didn't work, the directions you considered and set aside. Don't delete them — comment them out and leave them visible. The traces of your process are part of the work. Use <!-- * notation (Better Comments) to provide headings for each commented-out section.

Conceptual — choose one

A
A page about your childhood bedroom that gets progressively stranger or more distorted across versions.
B
A page about a person you know where each version reveals something different about them.
C
A page about a place where each version is a different emotional register — nostalgic, clinical, hostile, dreamlike.

Technical Requirements

  • Minimum 15 HTML elements — see W3 Schools HTML Reference
  • At least one image, hosted in the repo or linked from an external source

HTML Boilerplate

index.html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Your Title Here</title>
  </head>
  <body>

    <!-- your content goes here -->

  </body>
</html>

Deliverables

  • Repo named a1-git-labyrinth, linked from your username.github.io index page
  • A main branch and a develop branch
  • Minimum 20 commits with meaningful commit messages
  • At least 3 merge commits
  • 5 commits identified as significant versions, each on its own branch with a semantic name (e.g. glitchy-flower, early-attempt)
  • All branches pushed to GitHub
  • Each of the 5 commit URLs linked on your index page with a 1–2 sentence annotation describing what changed and why

On Tools and Problem-Solving

AI code-generation tools — ChatGPT, GitHub Copilot, Claude, and others — are one tool among many in this course. Others include browser developer tools, MDN Web Docs, Stack Overflow, the p5.js reference, your classmates, and your own experimentation. None of these is cheating. All of them are how developers actually work.

  • Use AI for specific problems, not entire pages
  • Paste the exact prompt you used as a comment directly above any AI-generated code
  • Your commit history is your accountability — frequent meaningful commits show genuine engagement over time
  • When stuck, try other routes: search [problem] site:stackoverflow.com, read MDN docs, open devtools and inspect something that already works, ask a classmate

Full comprehension of every line is not expected in a five-week course. What is expected is genuine engagement — tinkering, curiosity, and a willingness to sit with something until it does something interesting.

The Experienced Coder's Mindset

Every coder — including ones who have been doing this for fifteen years — regularly hits moments of "I can't do this," "I'm bad at this," "this will never work." This is not a sign that you're doing it wrong. It's a sign that you're doing it. The difference between an experienced coder and a beginner is not intelligence or ability — it's the quiet confidence that regardless of how many attempts it takes, a solution exists and you will eventually find it.

When you're stuck: take a break. Read Stack Overflow threads. Work on a different part of the page. Explain out loud to a friend — or to no one — what you're trying to do and what isn't working. And sometimes the seventh approach that isn't working the way you intended turns out to be more interesting than what you originally planned. Follow that.
